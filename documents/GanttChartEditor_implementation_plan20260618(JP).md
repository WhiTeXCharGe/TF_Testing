# GanttChart エディタ — 実装計画（進捗報告）

**日付：** 2026-06-18  
**状況：** フェーズ 1〜2 進行中（UI ほぼ完成）

---

## 1. 目的

既存の 2025年版・2026年版 GanttChart エディタを置き換える新しいエディタを構築する。  
このエディタは、YAML スケジュールデータを読み込み、ガントチャート上で割付を視覚的に編集し、  
最終的にはスケジューラ Webapp へ提出する機能を持つ。

---

## 2. 参照元

| 参照元 | 利用方法 |
|---|---|
| **2025年版（Python）** | UI レイアウト・機能の参考 — ボタン・ビュー・ダイアログの設計仕様として利用 |
| **2026年版（Tauri）** | ソースコードの参考 — 状態管理パターン（Context + Reducer）、TypeScript 型定義、ファイル解析ロジック |
| **新規構築部分** | 描画コンポーネント、ガントライブラリ統合、ファイル抽象化層、サービスエンドポイント |

> 2025年版を**設計仕様書**として、2026年版を**コードベース**として使用する。  
> 新しいアプリは両者の良い点を組み合わせたクリーンな再構築版。

---

## 3. 技術スタック

### フロントエンド

| 層 | 技術 |
|---|---|
| フレームワーク | React 19 + TypeScript |
| ビルドツール | Vite 5 |
| チャート描画 | カスタム HTML/CSS ガント（複数バー行対応） |
| 状態管理 | React Context + useReducer |
| YAML 解析 | js-yaml |

### バックエンド

| フェーズ | 技術 | 理由 |
|---|---|---|
| フェーズ 3〜5（開発中） | **Node.js + Express** | `web/service/server.js` として既に存在。拡張が容易で開発中の実行が簡単 |
| フェーズ 6（デスクトップアプリ） | **Rust（Tauri 経由）** | スタンドアロン `.exe` としてパッケージング時に Node.js を置き換え — 別サーバー不要 |

> バックエンドは開発速度を優先して Node.js から開始する。  
> デスクトップアプリ構築時（フェーズ 6）に同じロジックを Rust の Tauri IPC コマンドとして書き直す。  
> フロントエンドのコードは**両者で変更なし** — サービス層のみが切り替わる。

**言語：** UI テキストは日本語。コード・変数名は英語。

## 4. 実装フェーズ

```
フェーズ 1〜2  │  フロントエンド Web アプリ（現在）
              │  YAML を読み込み、ガントを表示、ブラウザ上で割付を編集
              │  バックエンド不要
              │
フェーズ 3〜4  │  Node.js サービス層（既存の web/service/server.js を拡張）
              │  重い制約チェックのエンドポイント
              │  バリデーション API
              │
フェーズ 5    │  GanttChart ↔ スケジューラ Webapp を接続
              │  送信 → Webapp の新規実行ダイアログを開く
              │  結果表示 → GanttChart を開く  ← デモ完成マイルストーン
              │
フェーズ 6    │  Tauri デスクトップアプリとしてパッケージング
              │  Node.js バックエンドロジックを Rust に書き直し
              │  ブラウザや Node.js なしで動作可能
```

- **サイドパネル** — 選択した割付の詳細表示、計画柔軟性の編集
- **スクロール同期** — 左の行ヘッダーパネルがチャートの縦スクロールに追従
- **CSS ドラッグ** — バーを左右にドラッグ・リサイズ可能、遅延なしにスムーズ
- **ダークネイビー UI** — 統一されたカラーテーマ

| ボタン | 場所 | 機能 |

### 8.6 制約チェック — フロントエンド vs バックエンド

#### どの制約をどこで行うか

制約の種類は多く、性質も様々。バーの重複チェックのような単純なローカルチェックはブラウザで即時実行できる。  
しかし、全作業者・全地域・全日付を横断する複雑なチェックはフロントエンドには重すぎるため、Node.js バックエンド（後に Rust）で行うべき。

| 制約名 | 内容 | フロント / バック |
|---|---|---|
| 作業時間 | 1日の作業時間が定義範囲内か | **フロントエンド** — 各バーへのシンプルな範囲チェック |
| スキルマップ | 作業者のスキルが作業に合っているか | **フロントエンド** — 割付作成時に参照テーブルで確認 |
| 同一日作業重複禁止 | 同一作業者が同日に複数作業をしていないか | **フロントエンド** — 同一作業者バーを高速スキャン |
| 最小・最大作業者数 | 1日の作業者数が範囲内か | **フロントエンド** — 作業ごとに1日あたりの割付数をカウント |
| 作業不可日 | 作業者の不可日に割り当てていないか | **フロントエンド** — 作業者の不可日リストと日付照合 |
| 工程開始日・終了日 | 各工程の全作業が期間内に収まっているか | **フロントエンド** — 工程ごとの日付範囲チェック |
| 初工程開始日固定 | 最初の工程が定義された開始日から始まっているか | **フロントエンド** — 単一の日付比較 |
| 工程間順序 | 先行工程の全作業完了後に後続工程が開始しているか | **バックエンド** — 工程内の全割付を横断して完了確認が必要 |
| 必要作業量 | 総作業時間が必要量を満たし、かつ過剰でないか | **バックエンド** — 全作業者の割当時間を集計して必要量と比較 |
| 移動日制 | 異なる地域間の割り当て間に移動日があるか | **バックエンド** — 地域・移動日データを用いた割付間クロスチェック |
| 作業責任者制約 | 各作業種別に責任者が割り当てられているか | **バックエンド** — 全割付を検索して責任者の存在確認 |
| 滞在期間制約 | 同国への連続・年間滞在日数が上限内か *(未適用)* | **バックエンド** — 作業者ごとの全渡航を集計してカウント |
| 残業時間制約 | 月・年間の残業時間が上限内か *(未適用)* | **バックエンド** — 作業者ごとの時間を期間集計 |
| 地域適性 | 作業者が特定地域で作業不可でないか *(未適用)* | **バックエンド** — 作業者 × 地域の適性マトリクス確認 |
| 企業適性 | 作業者が特定企業で作業不可でないか *(未適用)* | **バックエンド** — 作業者 × 企業の適性マトリクス確認 |

#### 制約チェックをいつ実行するか

**オプション A — バー移動のたびにリアルタイム実行**

| | 詳細 |
|---|---|
| **メリット** | 違反を即座に確認できる。確認ボタンを押す必要がない |
| **デメリット** | フロントエンド制約はリアルタイム実行できるが、バックエンド制約は不可。ドラッグのたびに API を呼ぶと遅延が大きくなり、リクエスト数も多くなりすぎる |
| **判定** | フロントエンドのみの制約には有効。バックエンド制約には現実的でない |

**オプション B — 「制約チェック」ボタンを押したときのみ実行（オンデマンド）**

| | 詳細 |
|---|---|
| **メリット** | バックエンド制約を含む全制約を実行できる。パフォーマンス問題なし。ユーザーが任意のタイミングで確認できる |
| **デメリット** | ユーザーがボタンを押すまで違反に気づかない可能性がある |
| **判定** | バックエンド制約に対しては唯一現実的な手段 |

**オプション C — ハイブリッド方式（推奨）**

- **フロントエンド制約** → バー移動後に自動実行（即時、API 呼び出しなし）
- **バックエンド制約** → ユーザーが **「制約チェック」** ボタンを押したときのみ実行

これにより、単純な問題（重複、スキル不一致、作業不可日）については即時フィードバックを提供しながら、  
重い制約はオンデマンドで実行するという最適なバランスが実現できる。

**要確認事項：**「制約チェック」ボタンはツールバーに常時表示すべきか、メニュー内に入れるべきか？  
また、違反はバーの赤ハイライト表示・ポップアップリスト表示、あるいはその両方で表示すべきか？
