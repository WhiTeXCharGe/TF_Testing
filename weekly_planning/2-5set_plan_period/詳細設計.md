# 2-5 計画期間決定ツール 詳細設計

## 1. 目的

2-4で作成したScheduleとEnvConfigを入力し、最適化に使用する計画期間を決定する。計画開始日より前に作業予定日があるassignmentは、行を分割せずassignment全体をFixedにする。

## 2. 対象範囲

### 対象

- 計画期間の開始日・終了日の算出
- 開始日前の日付を含むassignmentのFixed化
- ScheduleおよびEnvConfigの出力
- （オプション）`--plan-start` による計画開始日の上書き

## 3. CLI

入力・出力ファイルは必須の名前付き引数で個別に指定する。計画開始日の上書きは任意引数で指定できる。

| 引数 | 内容 |
|---|---|
| `--input-schedule` | 入力Schedule YAMLのパス |
| `--input-env-config` | 入力EnvConfig YAMLのパス |
| `--output-schedule` | 出力Schedule YAMLのパス |
| `--output-env-config` | 出力EnvConfig YAMLのパス |
| `--plan-start YYYY/MM/DD` | 計算された開始日を指定日で上書きする。phaseの日付は変更しない。省略時は通常の計算結果を使用する。 |

4つのパスは、`Path.resolve()` で解決し `os.path.normcase()` で正規化した文字列を比較する。重複があれば出力前にエラーとする。異なるパスを持つハードリンクなど、正規化後の文字列だけでは判別できない同一ファイルは検出しない。出力先に既存ファイルがある場合は上書きする。出力先の親ディレクトリは必要に応じて作成する。

## 4. 入出力データ

### 4.1 Schedule

入力Scheduleは、次のいずれかの形式を受け付ける。

- 直下に `plan_range`、`workflow_task_list`、`assignment_list` などを持つ形式
- トップレベルの `schedule` キーの下にScheduleを持つ形式

入力形式を出力でも維持する。計画期間およびassignmentの柔軟性以外のSchedule情報は変更しない。

ScheduleはYAMLとして読み書きする。YAMLのデータ内容を保持し、キー順は入力順を維持する。コメント、空白などの元のテキスト書式は保持対象外とする。

形式の選択は既存の `prepare_schedule.read_prev_flexible` と同様に、トップレベルに `schedule` キーがあればその値を使用し、なければ直下を使用する。直下と包装形式の両方にSchedule相当の値がある場合も、包装形式を優先する。このツールが実際に検証する範囲は「8. 入力検証とエラー」を参照する。

### 4.2 EnvConfig

EnvConfigは存在・読み取り可否のみを確認し、YAMLとして解析しない。内容を変更せず、入力ファイルのバイト列を出力先へ複製する。

## 5. 計画期間の算出

計算対象は、入力Scheduleの `workflow_task_list` に含まれる全workflowの全 `phase_task_list` とする。各phaseの `start_date` と `end_date` を候補日として使用する。

実行環境のローカル日付を `today` とし、Kを7日、Lを30日とする。加算する日数は土日祝を区別しない暦日とする。

phaseが1件以上ある場合は、次のように計画期間を決める。

```text
plan_start = max(phase start_date の最早日, today + K日)
plan_end   = max(phase end_date の最遅日 + L日, plan_start + L日)
```

phaseが0件の場合も正常に処理し、`plan_start` を `today + K日`、`plan_end` を `plan_start + L日` とする。システム全体として計画不要を判定する方法は未検討であり、このツールでは判定しない。

`--plan-start` が指定された場合は、phaseの件数にかかわらずその日付を `plan_start` として使用し、その開始日を基準に `plan_end` を決める。算出または指定した開始日と終了日をScheduleの `plan_range.start_date` および `plan_range.end_date` に設定する。入力のphase日付は変更しない。

phase・assignment・稼働日・`--plan-start` の日付の解釈は既存の `prepare_schedule.ymd` を流用し、計画期間の日付は `YYYY/MM/DD` 形式で出力する。文字列は前後の空白を除き、`-` を `/` に置換した先頭10文字を日付として解釈するため、先頭が解釈可能なら末尾に文字があっても受け付ける。YAMLから読み込まれた日付型も受け付ける。

phaseの `start_date` または `end_date` が欠落・不正な場合は、ファイル形式の不正として処理全体をエラーとし、どのphaseも除外して算出しない。既存の `ymd` による日付解釈に加えて前後関係を検査し、`start_date` が `end_date` より後の場合もエラーとする。

## 6. AssignmentのFixed化

`assignment_list` の全行を対象に、各行の `work_date_list[].date` を判定する。

- 計画開始日より前の日付が1日以上含まれる場合、そのassignment行全体の `plan_flexibility` を `Fixed` にする。
- assignment行は分割せず、`start_date`、`end_date`、`work_date_list` およびその他の項目は変更しない。
- 開始日より前の日付を含まない行は、`plan_flexibility` を含め変更しない。
- 既に `Fixed` の行はそのまま維持する。
- `plan_flexibility` が省略されていても、開始日前の日付がある行には `Fixed` を設定する。

assignmentの `start_date`・`end_date` が欠落または不正な場合、開始日が終了日より後の場合、`work_date_list` が欠落または空の場合、リスト内の日付が不正な場合、および稼働日がassignmentの `start_date` から `end_date` の範囲外にある場合は、ファイル形式の不正として処理全体をエラーとする。期間の両端と最初・最後の稼働日が一致する必要はない。

## 7. 処理手順

1. 4つの必須パス引数と、指定されていれば `--plan-start` を読み取る。
2. 4パスが重複していないことを確認する。
3. 入力Scheduleを読み込み、直下形式または `schedule` 包装形式を特定する。
4. Scheduleを検証し、入力EnvConfigの全バイトを読み込む。不正または読み込み失敗の場合はエラーを明示し、出力せずに終了する。
5. 計画開始日を算出する。`--plan-start` があればその日付を開始日とし、確定した開始日に基づき終了日を算出する。
6. Schedule内の全assignmentを走査し、該当行をFixedにする。
7. 出力Scheduleの親ディレクトリを作成し、YAMLとして書き出す。
8. 出力EnvConfigの親ディレクトリを作成し、入力EnvConfigをバイト列で複製する。

既知の入力検査と計算を完了してから出力を開始する。ファイルの読み書きに失敗した場合はエラーを明示する。ScheduleとEnvConfigの2ファイルを一括更新するトランザクション保証は設けないため、出力中の失敗では片方だけ更新される可能性がある。

## 8. 入力検証とエラー

Scheduleの構造について、以下を検証する。

- トップレベルと選択されたScheduleはマッピングとする。
- Scheduleには `plan_range`、`workflow_task_list`、`assignment_list` が必要。`plan_range` はマッピングで、`start_date` と `end_date` のキーが必要。元の計画期間の日付値は検証せず、算出結果で上書きする。
- `workflow_task_list` はリストで、各workflowはマッピングかつ `phase_task_list` を持つ。`phase_task_list` はリストで、各phaseはマッピングとする。phaseの日付は「5. 計画期間の算出」のとおり検証する。
- `assignment_list` はリストで、各assignmentはマッピングとする。`work_date_list` は空でないリストで、各要素はマッピングかつ有効な `date` を持つ。assignmentの日付と稼働日の範囲は「6. AssignmentのFixed化」のとおり検証する。
- `plan_flexibility` は省略可能。指定された場合は文字列の `Flexible`、`Reluctant`、`Fixed` のいずれかとする。

上記以外の項目については、このツールでは検証しない。

引数不足や不正な `--plan-start` は `argparse` がエラーを標準エラー出力に表示し、終了コード2で終了する。Scheduleの検証不正は `ValueError` を送出し、YAMLの解析やファイルの読み書きに失敗した場合も例外を送出する。CLIでは未処理例外として標準エラー出力に表示され、非ゼロで終了する。正常時は出力先を標準出力に表示し、終了コード0で終了する。

入力検証・入力読み込み・計算に失敗した場合は出力を開始しない。出力開始後の失敗については、ファイルが途中まで書かれたり、片方だけ更新されたりする可能性がある。

## 9. 実装上の制約

- 正規化後も異なるパスで同じ実ファイルを参照する場合は、重複を検出できないことがある。
- ファイル仕様の全項目を検証する汎用スキーマ検証は行わない。
- 計画不要の判定と、2ファイル出力のトランザクション保証は行わない。

## 10. テスト観点

以下は確認すべき観点であり、すべてが現在の自動テストで個別に検証済みという意味ではない。

- phaseがある場合に最早開始日と `today + K日` の遅い方を採用し、最遅終了日と確定した開始日それぞれにL日を加えた日の遅い方を終了日に採用する。
- phaseが0件の場合、開始日を `today + K日`、終了日を開始日+L日とする。
- phaseの有無にかかわらず `--plan-start` が指定された場合、指定日を開始日に採用し、その日を基準に終了日の下限を決める。
- phaseの `start_date` / `end_date` が欠落または不正な場合は、処理全体をエラーとし、両出力ファイルを書き出さない。
- phaseの `start_date` が `end_date` より後の場合は、処理全体をエラーとし、両出力ファイルを書き出さない。同日の場合は前後関係によるエラーとしない。
- `work_date_list` が欠落・空・不正日付の場合、およびassignmentの期間と稼働日が矛盾する場合は、処理全体をエラーとし、両出力ファイルを書き出さない。
- 上記の入力ファイルの不正に該当する場合は、処理全体をエラーとし、両出力ファイルを書き出さない。
- 開始日前の稼働日を含むassignmentは、開始日をまたぐ場合も含め、分割せず行全体をFixedにする。
- 開始日当日以後のみのassignmentは変更せず、既にFixedのassignmentも維持する。
- 稼働日の全てがassignment期間内にあれば、期間の両端と稼働日が一致しなくてもエラーにしない。
- 直下形式と包装形式が両方ある場合は包装形式を優先する。
- EnvConfigは読み取り可能ならYAMLとして解析せず、バイト列をそのまま出力する。

現在の自動テストは `tests/test_set_plan_period.py` にあり、期間算出・開始日上書き・直下／包装形式・Fixed化・EnvConfig複製・一部の入力不正・パス重複・不正な開始日引数を確認する。例えば、包装形式の優先、phaseの同日開始・終了、欠落した稼働日リストは個別のテストケースとしては未追加。

ツールフォルダーでの実行例：

```powershell
python -m unittest discover -s tests -v
```
