# 2-4 apply_seiban_list 設計書

## 1. 目的

2-4 は、その週に**新しく追加された製番(モジュール)**を計画に取り込むツールです。これまで計画ツール(GanttChartEditor)で手作業していた「新しいモジュールの追加」を置き換えます。

製番リストのブックを読み、**2つの yaml の両方**を更新します。

- **EnvConfig**: 新しい顧客・Fab・Region・ワークフロー(工程テンプレート)を追加し、新しい作業(operation)に対する作業者のスキルを追加します。
- **Schedule**: 新しい製番ごとに workflow task を1つ作ります。削除対象の製番の workflow task は取り除きます。

フローの中での位置(出力の番号は今後変わる可能性があります):

| ツール | 入力 | 出力 |
|---|---|---|
| 2-2 + 2-3 | 前週の計画、SU_Others など | `01_EnvConfig.yaml`、`01_Schedule.yaml` |
| **2-4** | `01_*`、製番リストのブック | `02_EnvConfig.yaml`、`02_Schedule.yaml`、レポート(`--report`) |
| 2-5 | `02_*` | `03_*` |

2-4 はブックを**読むだけ**です。処理後の色替え(白→グレー、ピンクの行の削除)は、ブック側のマクロが行います。

## 2. 2-4 がやらないこと

- **グレーの行**(すでに計画済みの製番)には触れません。内容が変わっていた場合は 2-2-3 が扱います(変わったモジュールは misc タスクになります)。そのために 2-2-3 を後で変更する可能性があります。
- **テンプレートの変更**(工数の変更、作業の追加・削除、モジュールのテンプレート入れ替え)と、既存 id の**名前変更**は扱いません。変更されたテンプレートはどのワークフローとも一致しないため、新しいワークフローが作られ、古いものはそのまま残ります(5.2)。本格的な扱いはチームで決めます。
- 既存のワークフロー・顧客・Fab・Region は、削除も名前変更もしません。
- `plan_range` は変更しません(期間は 2-5 が設定します)。
- 装置名称の列は、今は使いません。

## 3. 入力: 製番リストのブック

読むシート:

| シート | 用途 |
|---|---|
| `計画対象` | 処理する行。列は、登録日時、製番、装置名称(未使用)、顧客、Fab、Region、開始可能日(未使用)、希望納期(未使用)、工程選択、工程1〜4の開始可能日・終了期限日 |
| `搬入先テーブル` | 搬入先、顧客、Fab、Region。`計画対象` で Region が空のときの補完に使います |
| `工程テンプレート<N>` | テンプレートごとに1シート。工程番号、作業番号、作業名、工数、最小人数、最大人数 |

`製番リスト`(マスターの一覧)と `データ抽出` は読みません。

### 行の色(製番のセルの色)

| 色 | 意味 | 2-4 の動作 |
|---|---|---|
| なし / 白 | 新しい製番 | 追加 |
| グレー `D9D9D9` | 計画済み | 無視 |
| ピンク `FFDCE6` | 削除する | 削除 |
| それ以外の色 | 不明 | スキップし、レポートに記載 |

### 正規化

- 製番: `common.text.tool_code` のモジュールコードの規則で正規化します。モジュールコードでないセルの行は、スキップしてレポートに記載します。
- 顧客・Fab・Region の名前: キー(NFKC、空白なし、大文字小文字を区別しない)で比較します。余分な空白や全角文字で重複が作られるのを防ぐためです。新規の登録にはシートの文字(前後の空白のみ除去)をそのまま使います。
- 作業名: 前後の空白を除き NFKC に揃えます。`Q/C` は `QC`(EnvConfig の名前)として扱います。

## 4. マスターデータ(EnvConfig)

有効な白い行に必要なものだけを作成・更新します。

| 項目 | ルール |
|---|---|
| 顧客 | 名前キーで照合。新規は空き番号の `c<n>`、使用不可日なし |
| Region | 名前キーで照合。新規は空き番号の `r<n>`。値はデコーダと同じ既定値(最大滞在・年間滞在 10000、滞在休止間隔 3、使用不可日なし)。新しい Region と既存の全 Region の間に、双方向で移動日数 1 日の行を追加 |
| Fab | **顧客 + Fab 名**で照合。別の顧客の同名 Fab は別の Fab として扱います。新規は空き番号の `f<n>`(顧客と Region を設定) |
| Fab 名が空の顧客 | 顧客名と同じ名前の Fab を使います(Schedule には必ず Fab id が必要なため) |
| Region が空 | `搬入先テーブル`(同じ顧客・Fab)から補完。それでも空なら `r_other` とし、レポートに記載 |
| 顧客が空 | `c_other`(顧客も Fab も空なら Fab は `f_other`) |
| 既存 Fab と Region が違う | Fab の Region を行の Region に**更新**し、レポートに記載 |

行と `搬入先テーブル` の食い違いはレポートに記載します。行の値を優先します。

## 5. ワークフロー(工程テンプレート)

### 5.1 テンプレートの内容

テンプレートのシートは、工程番号 P と作業番号 K ごとに、作業名・工数・最小人数・最大人数を持ちます。工程1(または他の番号)がないテンプレートもあります。シートに存在する工程だけを使い、テンプレートにない工程の日付は無視します。

### 5.2 一致するか、新規作成か

有効な白い行が使うテンプレートごとに:

1. 作業の構成が同じ**既存ワークフロー**を探します。工程番号、作業番号、作業名、最小人数・最大人数が同じものです(id、名前、`work_hours` は比較しません)。
2. 見つかった場合: それを使います。既存のワークフロー(`wf_tool` のような古いものを含む)はそのまま残します。
3. 見つからない場合: **新しいワークフローを作成**します。

そのため、テンプレートが変更されても古いワークフローは書き換えず、新しいものが作られます。古い `wf_tool` は最小人数・最大人数が異なるため、初回はおそらくテンプレート2と一致せず、新しいワークフローが作られ、既存のモジュールは `wf_tool` のまま残ります。

### 5.3 新しいワークフローの id

`n` = EnvConfig 内の最大の `wf<数字>` + 1(数字のない古い id は無視。最初は `wf1`)。

| 項目 | id | 名前 |
|---|---|---|
| ワークフロー | `wf<n>` | `wf<n>` |
| 工程 P | `wf<n>p<P>` | `p<P>` |
| 作業 K | `wf<n>p<P>o<K>` | 作業名(`Mech`、`Elec`、`QC`) |

作業のフィールド: `work_hours: [10]`(現状と同じ)、`min_worker_num` と `max_worker_num` はテンプレートの値(従来の 1 と 8 ではありません)。ソルバーは工程番号を工程 id の最後の `p<数字>` から求めるため、`wf1p1` は工程1になります。

### 5.4 作業者のスキル

ワークフローを作成するとき、作業者ごと・**新しい**作業ごとに:

- 作業者の `skill_map` にある、**同じ名前**の既存の作業(どのワークフローのものでも)を集めます。
- 新しい作業には、それらのうち**最も高い**レベルと、そのレベルの作業の `worker_type_by_operation` の値を設定します。
- 同じ名前の作業がない場合: その作業のスキルは付けません。

既存のどの作業にもない作業名は、誰もできないことになります(レポートに記載のみ)。`other_op` などのエントリには触れません。

## 6. Schedule

### 6.1 白い行 → 新しいモジュール

まず行を検査します: 製番が有効、テンプレートのシートがあり内容が有効、テンプレートの全工程に開始日・終了日がある、終了が開始より前でない。無効な行はスキップしてレポートに記載し、何も作りません(マスターもワークフローも作りません)。すでに Schedule に workflow task として存在する製番は、警告を記載してスキップします。

有効な行からは workflow task を1つ作ります:

| フィールド | 値 |
|---|---|
| モジュール id | 空き番号の `e<n>` |
| `name` | 製番 |
| `workflow`、`fab` | 5 と 4 の id |
| phase task | id は `<モジュール><pP>`(例: `e57p1`)、`phase` は工程 id、名前は `p<P>`、開始・終了は工程 P の開始可能日・終了期限日 |
| operation task | id は `<モジュール><pP>o<K>`、`operation` は作業 id、`workload_hours` はテンプレートの工数 |
| 書かないもの | `recommends_worker_min/max`(ソルバーは空を「推奨なし」として扱います) |

task id は `e57p1o1` の短い形のままにします。ソルバーは operation task の id を `...p<数字>o<数字>` のパターンで分解するため、`e57wf1p1o1` のような長い id は、未知の task を読むときに誤った位置で切られるおそれがあるためです。

### 6.2 ピンクの行 → 削除

その製番の workflow task がある場合: その phase task と operation task、および**その operation task を参照するすべての assignment 行**を取り除きます。これらの assignment は構造上 flexible です(計画担当者が触った製番や過去の製番は misc タスクになっており、workflow task を持ちません)。残しても Timefold が再計画します。workflow task がない場合(Fixed、過去、または未計画): 何もせず、レポートに1行記載します。

同じ製番が白とピンクの両方にある場合: 両方の行をスキップしてレポートに記載します。

### 6.3 処理順

1. ブックを読み、すべての行を検査 → 2. 削除(ピンク) → 3. 有効な白い行に必要なマスター・ワークフロー・スキルを作成 → 4. モジュールを追加(白) → 5. ファイルとレポートを書き出し。

## 7. 出力とオプション

- `02_EnvConfig.yaml` と `02_Schedule.yaml` を `--out-dir` に書き出します(番号は変わる可能性があります)。入力ファイルは上書きしません。
- ターミナルには件数だけを表示します(追加・削除・スキップした行、作成したマスターとワークフロー、警告の数)。**警告はすべてレポートに書き**、`--report` を付けたときだけ `<名前>_apply_report.txt` に出力します(2-2-3 と同じ)。
- オプション: `--schedule`、`--env`、`--seiban-list`、`--out-dir`、`--sheet`(既定は `計画対象`)、`--report`。2-6 / 3-1 のような `config.txt` は後から追加できます。

## 8. コード構成とレビューの段階

- `common/` には、他のツールでも使える読み取り処理(製番リストとテンプレートの Excel 読み取り)を置きます。2-4 だけで使う処理はツールのフォルダに置きます。ツール同士は import しません。
- 段階 A: ブックを読み(色つきの行、テンプレート、搬入先)、単純なデータにする。小さな自動生成ブックでテスト。
- 段階 B: EnvConfig の更新(マスター、ワークフローの照合と作成、スキル)。単純なデータを扱う関数として作る。
- 段階 C: Schedule の更新(追加・削除)、コマンドライン、レポート、README。

## 9. 他のツールへの影響と未決事項

- **2-2-3(後で必要):** `common/worker_skills.py` は役割の文字を固定の id `p2o1 ... p4o1` に対応づけています。2-4 が `wf<n>...` の作業を作ると、次週の 2-2-3 はそれらのスキルを落としてしまいます。EnvConfig を使って、作業の**名前**で対応づける必要があります。
- **セル名:** 顧客名と同じ名前の Fab を使うと、3-2 / 3-3 のセル名(`<顧客><Fab>_...`)で名前が重複します。Fab が顧客名と同じ場合は省く形にできます。
- **照合に最小人数・最大人数を含める**(5.2): この方針でよいか、チームで確認してください。
- **日付が欠けている行はスキップ**(6.1): これでよいか確認してください。
- **搬入先:** 行と `搬入先テーブル` が食い違うときは行を優先します(4): これでよいか確認してください。
- **テンプレートの変更・入れ替え:** チームで相談して決めます。
