#  連続計画負荷測定

初期状態では **30 台**の装置から開始し、**2.5 台／営業日**のレートでモジュールを増設した。  
まず **300 台**到達を目標とし、300 台に到達したあと、最終ステップでさらに **1 台**追加し、最終的な総装置数は **301 台**となる。

全ステップ共通で `EQ_EVAL_DAYS = 5` を使用し、**5 営業日ごと**（1 ブロック）にスケジューラを再評価しながら、cut-off date をブロック単位で前に進めている。

同一入力・同一シードの条件で、次の 2 パターンを比較した。

- **Trim ON**  
  `TRIM_FINISHED_MODULES = true`。  
  各モジュールのフェーズがすべて終了し、かつその終了日が現在の `cut_off_date` より前になっているものを「完了モジュール」とみなし、  
  対応する `TaskWindow` と fixed アサインをモデルから削減する。

- **Trim OFF**  
  `TRIM_FINISHED_MODULES = false`。  
  過去に終了したモジュールも含め、すべてのモジュール／アサインをモデル上に残したまま、同じ条件でスケジューリングを実行する。

結果テーブルでは、各ステップについて以下の項目を記録している。

- **Order**  
  各評価ステップの通し番号。

- **Cut-off-date**  
  そのステップで `schedule.cut_off_date` に書き込まれた日付。  
  この日より前に開始するアサインは `plan_flexibility = Fixed`、  
  当日以降に開始するアサインは `Flexible` として扱われる。

- **追加（台）**  
  その 5 営業日のブロック内で新規に作成された装置モジュール数。

- **総装置数（台）**  
  追加後に `workflow_task_list` 上に存在する装置モジュールの総数。  
  初期 30 台から開始し、最終的に **301 台**まで増加する。

- **実行時間（分）**  
  各ステップにおける Java 実行時間（分）。  
  `IncrementalSchedulerRunner` ＋ `EmployeeSchedule` の一連の処理時間を計測している。

- **Fixed/Flexible**  
  そのステップ時点の `assignment_list` 内アサイン件数を、  
  `plan_flexibility = Fixed` と `Flexible` に分けてカウントしたもの。

- **絶対制約違反（Hard）**  
  Hard スコアに対応する絶対制約違反の件数。  
  値が 0 の場合、そのステップのスケジュールはすべての Hard 制約を満たしていることを意味する。
